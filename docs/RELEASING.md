# Releasing

Releases are built and published by `.github/workflows/release.yml` on
`windows-latest`.

## Versioning

Use `MAJOR.MINOR.PATCH` for the Rust package version and a matching `v` tag.

1. Update `version` in `Cargo.toml`.
2. Refresh the lockfile so `--locked` builds accept the new version:

   ```bat
   cargo update -p taskbar-stats --offline
   ```

   This only rewrites the `taskbar-stats` entry in `Cargo.lock`. Skipping it
   fails the release build with "cannot update the lock file because
   `--locked` was passed".

3. Run the local checks:

   ```bat
   scripts\build.bat --release
   cargo fmt -- --check
   cargo clippy --all-targets -- -D warnings
   cargo test --all-targets
   ```

4. Commit the version bump and the lockfile together.
5. Create and push an annotated tag:

   ```bat
   git tag -a v0.1.0 -m "Taskbar Stats v0.1.0"
   git push origin main --tags
   ```

The release workflow rejects a tag that does not match `Cargo.toml`. It exports
`TASKBAR_STATS_VERSION=v<version>` before compiling, so the version in the panel
footer comes from the release tag. Local builds fall back to the Cargo package
version.

## Preparing a release

`prepare-release.yml` performs the version bump and tag creation so the two
cannot drift apart. It has two entry points.

**Automatic, on merge.** Add a footer to the commit that lands on `main`:

```text
Release-As: 0.2.0
```

Edit the commit message in GitHub's merge dialog (or the squash commit message).
A pull request description is only used if your merge method copies it into the
commit. On push, the workflow reads the footer, runs `scripts/bump_version.py`,
commits `chore(release): bump version to 0.2.0`, tags `v0.2.0` on that commit,
and pushes both. The tag push starts `release.yml`.

**Manual.** Actions → **Prepare release** → *Run workflow*. Leave `version` empty
to bump the current version by `patch`, `minor`, or `major`, or type an exact
version. A manual run always releases `main`.

Both paths require the `RELEASE_TOKEN` secret. The workflow fails fast without
it, because a tag pushed with `GITHUB_TOKEN` does not start another workflow run.
The same token makes the release page show a real account instead of
`github-actions[bot]`.

Re-running is safe. On a push, a commit whose subject starts with
`chore(release):` is skipped, so the workflow's own bump commit does not loop;
a manual run ignores that guard so a half-finished release can be completed. A
version already present in `Cargo.toml` produces no commit. An existing
`v<version>` tag ends the run.

Only tag commits that are on `main`. `release.yml` has no branch filter, so a tag
pushed from a feature branch releases that commit even if it was never merged.

## Release notes

The GitHub release title is the tag itself, for example `v0.2.0`. The body is
generated by `scripts/release_notes.py` from the conventional commits between
the previous version tag and the new tag, so write commits with conventional
prefixes. Each bullet ends with the short commit hash linked to its commit on
GitHub.

| Commit type | Section |
| --- | --- |
| `feat` | Added |
| `fix`, `revert` | Fixed |
| `perf`, `refactor` | Changed |
| `remove` | Removed |
| `build`, `chore`, `ci`, `docs`, `style`, `test` | Omitted |

- `!` after the type or a `BREAKING CHANGE:` footer prefixes the entry with
  `**Breaking:**`.
- `#123` references in the subject or body are collected and appended in numeric
  order.
- External authors and `Co-authored-by` trailers with GitHub noreply addresses
  add `thanks @user`; the repository owner and bots are skipped.
- Commits without a conventional prefix fall back to the Changed section. If a
  release only contains omitted types, every commit is listed under Changed.
- Sections with no entries are left out.

Preview the notes locally:

```bat
python scripts/release_notes.py --from v0.1.0 --to HEAD --repo OWNER/REPO
```

Without `--repo` the hash is printed as plain text instead of a link.

## Release author

GitHub attributes a release to the owner of the token that created it, not to
the account that pushed the tag. With the default `GITHUB_TOKEN` that owner is
`github-actions[bot]`, which is why the release page says
"github-actions released this".

The workflow reads an optional `RELEASE_TOKEN` secret so a real account owns the
release. Set it to a personal access token (classic `repo` scope, or fine-grained
with `Contents: read and write`) belonging to the maintainer who publishes
releases. When the secret is present, the release shows that account instead.

There is no way to derive a per-pusher token from `github.actor`; the author is
always the token owner. Set `RELEASE_TOKEN` to the account that cuts releases.

## Artifacts

The workflow builds `target/release/taskbar-stats.exe`, compiles the Inno Setup
installer, and publishes:

```text
TaskbarStats-<version>-windows-x64.zip
TaskbarStats-<version>-windows-x64.exe
TaskbarStats-<version>-windows-x64-setup.exe
TaskbarStats-<version>-windows-x64.sha256
```

The zip contains the executable. The setup executable installs the app and
generates an uninstaller automatically. The checksum file covers both the zip and
the setup executable using the standard two-space format:

```text
<sha256>  TaskbarStats-<version>-windows-x64.zip
<sha256>  TaskbarStats-<version>-windows-x64-setup.exe
```

## Installer

The installer source is `installer/taskbar-stats.iss`. It targets the current
user, installs under `%LOCALAPPDATA%\Programs\TaskbarStats`, and does not require
elevation.

To build it locally, install Inno Setup 6, build the release executable, then run:

```powershell
.\scripts\build-installer.ps1 -Version 0.1.0
```

The result is written to `dist/TaskbarStats-0.1.0-windows-x64-setup.exe`.

## Signing

Windows builds are currently **unsigned**. There are no signing secrets to
configure, and SmartScreen may warn on first run.

If code signing is added later, sign both the executable and the setup executable
before packaging them and update the verification step in `release.yml`. Do not
publish a signed label until the signatures have been verified.

## Local release build

```bat
scripts\build.bat --release
```

The local executable is written to `target\release\taskbar-stats.exe`. The icon
resource is compiled from `taskbar-stats.rc` and `assets/icon.ico` by `build.rs`;
the Windows SDK `rc.exe` must be available.
